Reviewer Demonstration Script

A complete, ordered script — exact commands, what to expect, what to point at, what to say. Written for someone nervous, with almost no coding background, standing in front of a reviewer.

Before you start

Do the file-generating steps (2 and 8 below) once, in private, before the reviewer arrives. Nobody needs to watch npm ci finish or a browser install progress bar — you want the live parts of the demo to be fast and predictable.

Before the Review

StepCommand
1. Install dependencies (only needed once, or after a fresh clone)
npm ci
npx playwright install --with-deps chromium
2. Confirm everything still verifies
npm run verify
3. Generate a fresh dashboard so it's ready to show
npm run generate:dashboard

All three should complete without error. If npm run verify shows any "failed" count above 0, stop and fix that before the review — it means something in the repository's current state doesn't match its own regression guards.

Starting the Review

What I should say

"I built an automated system that tests a demo shopping website for accessibility problems on every code change, and instead of just pass/fail on one run, it treats the accessibility defect count as a manufacturing-style measurement and applies Statistical Process Control to it — the same discipline used to monitor variation on a factory floor — so it can tell ordinary noise apart from a genuine regression. A quality gate acts on that distinction, and a dashboard shows the evidence."

(This is the 30-second answer from the Home page — reread it once beforehand so it comes out naturally.)

Showing the Project

Open docs/architecture/ARCHITECTURE.md and this guide's Architecture page side by side, or just walk through the layer diagram. Point out: "seven layers, each one hands a JSON file to the next — that's what lets me test the statistics without needing a browser running."

Running Accessibility Tests

npm run test:a11y

What it does: Playwright opens Chromium, visits all 8 ShopSmart pages, runs axe-core on each, and writes one new telemetry record.
Expected output: Playwright's test report — 8 tests, each confirming a scan completed (these tests check that a result came back, not that there are zero violations, since the point is to measure, not just pass/fail).
What to point out: a new file appears in telemetry/history/.
What to say: "Each of these tests scans one page and hands the raw result to a custom Playwright reporter, which turns the whole run into one telemetry record."

Showing Telemetry

Open the newest file in telemetry/history/ in a text editor (no command needed — this is just reading a file).

What I should say

"This is one build's permanent record. The important number is defectScore — it's a severity-weighted sum: critical defects count 10 points, serious 5, moderate 2, minor 1. That one number is what the statistics engine actually tracks over time."

Showing SPC

npm run verify:spc

What it does: read-only — re-derives the control chart and every rule against known fixtures and the real telemetry history, and checks the results match what's already validated.
Expected output: ends with === Results: 30 passed, 0 failed ===.
What to say: "This proves the control-chart math and every detection rule still behave exactly as I validated them — center line, sigma, control limits, the Western Electric and Nelson rules, trend, regression-spike, and CUSUM drift detection." Then walk through the concepts on the SPC From Zero page as needed.

Showing the Quality Gate

npm run gate:ci

What it does: evaluates the current telemetry history through the SPC engine and the gate policy, prints the verdict, writes telemetry/aggregated/gate-verdict.json, and exits 0 or 1.
Expected output: console lines showing status (PASS/WARN/FAIL), any reasons, and a final "Quality Gate: <STATUS> — CI continues." or "… — blocking the build."
What to say: "PASS and WARN both exit 0 — only FAIL blocks a merge. That's a deliberate policy choice: WARN is for signals worth a human noticing, not signals that should stop the whole team."

Showing the Dashboard

npm run serve:dashboard

What it does: regenerates the dashboard, then serves it at http://localhost:4310.
What to do: open that URL in a browser, and scroll through the three panels: Production Process, Experiment A, Experiment B.
What to say: "Everything on this page is read from a JSON file the SPC and gate engines already produced — the dashboard itself doesn't calculate anything. That's enforced by an automated check, not just something I'm asserting."

Showing CI/CD

This part happens on GitHub, not the terminal. Exact procedure:

  1. Open the repository on GitHub and go to the Actions tab.
  2. Select the Accessibility Quality Gate workflow.
  3. Either open a recent run (from a real push), or click Run workflow to trigger it manually (this is what workflow_dispatch is for).
  4. While it runs, point out the step list matches exactly what you just ran locally: verify scripts, the accessibility scan, "Evaluate Quality Gate," then dashboard generation and uploads.
  5. If a run ever shows red (failed), scroll to the "Upload quality evidence" step anyway and show it still ran — that's the if: always() behavior described on the CI/CD page.
What I should say

"This workflow is read-only against the repository — it never commits anything back. Any new telemetry a CI run produces only leaves the runner as a downloadable 30-day artifact. That was a deliberate choice to avoid the pipeline creating its own commits."

Showing the Experiments

npm run verify:experiment
npm run verify:stable-cohort

What they do: regenerate and independently re-verify both 30-build synthetic cohorts.
Expected output: === Results: 52 passed, 0 failed === and === Results: 30 passed, 0 failed === respectively.
What to say: "Real production history is only 4 builds — nowhere near enough to prove the statistics work. So I built two synthetic, seeded, reproducible cohorts: Experiment A has five deliberate phases, including a real regression I injected at build 23, to test the SPC methodology under changing conditions. Experiment B is a single deliberately stable regime, used only for capability analysis, because Cpk assumes stability and Experiment A doesn't have it on purpose." Then walk the Experiments page's timeline diagram if there's time.

Ending the Demo

What I should say (30-second close)

"So to summarize: this project takes accessibility testing, which normally only tells you pass or fail on one run, and turns it into a monitored process — using the same statistical control methods used in manufacturing quality engineering — so a CI pipeline can tell the difference between ordinary noise and a real regression, block on the real ones, warn on the borderline ones, and show the evidence for both. The contribution isn't a new statistical method or a new accessibility scanner — it's the bridge between those two established fields, applied and validated end to end."
