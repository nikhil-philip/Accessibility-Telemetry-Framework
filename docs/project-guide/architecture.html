System Design

Architecture: The Seven Layers

The project is organized as seven layers (L1–L7), each handing a well-defined artifact — usually a JSON file on disk — to the next. This is what makes the SPC and gating stages testable on their own, without a browser. The application being tested (ShopSmart) sits outside the numbering as "L0."

Who Calculates vs. Who Only Displays

This distinction matters a lot for a viva, because it's the strongest evidence that the architecture is sound: L7 (the dashboard) is not allowed to invent numbers.

  • L4 (Telemetry) calculates one thing: the weighted defectScore. Nothing else.
  • L5 (SPC) calculates everything statistical: center line, sigma, control limits, every rule flag, trend, spike, drift, Cpu.
  • L6 (Gate) calculates one thing: the PASS/WARN/FAIL decision, by comparing L4's and L5's numbers to policy thresholds.
  • L7 (Dashboard) calculates nothing. Its own source file says so directly. src/dashboard/dashboardDataBuilder.ts's header comment states it "performs zero SPC math, zero rule evaluation, zero gate policy logic, and zero score computation of its own." It calls loadTelemetryHistory(), computeSpcReport(), evaluateLatestBuild(), and runAnalysis()/summarizeResults() — all pre-existing L4/L5/L6 functions — and only groups their output into the shape the HTML template expects.
Technical explanation

scripts/verify-dashboard.ts enforces this as a regression guard, not just a design intention: it calls buildDashboardData() and then independently calls computeSpcReport(history) and evaluateLatestBuild(history) directly, and asserts the two results are byte-identical (modulo the generatedAt timestamp). If a future change accidentally made the dashboard compute its own number, this check would fail.

One Build, File by File

This is what actually happens, in order, naming the real functions — not a paraphrase.

  1. A developer pushes to main, or opens/updates a PR against main. GitHub Actions runs .github/workflows/accessibility-ci.yml.
  2. The workflow runs npm ci, installs the Chromium browser, and compiles TypeScript (npx tsc -p tsconfig.json).
  3. Six regression-guard scripts run (verify:spc, verify:gates, verify:experiment, verify:stable-cohort, verify:ci, verify:dashboard) — these check that the SPC engine, the gate engine, both experiments, and the dashboard's data layer still behave exactly as previously validated. They do not scan anything.
  4. npm run test:a11y runs Playwright against tests/accessibility/all-pages.a11y.spec.ts, which loops the 8 routes in src/config/sites.config.ts and calls makeAxeBuilder().analyze() (built from src/utils/accessibilityScanner.ts's createAxeBuilder()) for each one.
  5. Each test attaches its raw axe result as a Playwright test attachment named axe-results.
  6. A custom Playwright reporter, src/telemetry/reporter.ts (TelemetryReporter), collects every attachment in onTestEnd(), then in onEnd() calls collectTelemetry() (src/telemetry/collector.ts) once for the whole run.
  7. collectTelemetry() normalizes the raw violations, computes defectScore = 10·critical + 5·serious + 2·moderate + 1·minor via computeDefectScore(), and returns one TelemetryRecord.
  8. writeTelemetryRecord() (src/telemetry/writer.ts) writes it to telemetry/history/build-<commitSha>.json. This file is never opened for writing again by any other code path in src/.
  9. npm run gate:ci runs scripts/run-quality-gate.ts, which calls evaluateFromDisk() (src/gates/qualityGateEvaluator.ts). That function calls loadTelemetryHistory() (src/spc/spcEngine.ts) to read every record in telemetry/history/, then computeSpcReport() to get the full SpcReport, then evaluateQualityGate() against DEFAULT_GATE_POLICY to get a GateVerdict.
  10. formatGateVerdictForCi() (src/gates/ciAdapter.ts) turns the verdict into an exit code (0 for PASS/WARN, 1 for FAIL), GitHub Actions annotations, and a step-summary. run-quality-gate.ts writes the raw verdict to telemetry/aggregated/gate-verdict.json and exits with that code.
  11. Whatever the exit code, four more steps run because they're marked if: always(): generate:dashboard (which calls buildDashboardData()), test:dashboard, test:dashboard:a11y, and an artifact upload of dashboard/, telemetry/aggregated/, telemetry/history/, and reports/.
  12. GitHub reports the gate step's exit code as the PR's status check. A FAIL blocks merge if branch protection requires this check; PASS/WARN do not.

Where the Code Differs From ARCHITECTURE.md

The architecture document (docs/architecture/ARCHITECTURE.md, "Draft v1.0") was written to plan the system before all of it existed. Some details drifted during implementation. Being able to name these honestly is worth more in a viva than pretending everything matches — it demonstrates you understand the real system, not just the plan for it.

ARCHITECTURE.md saysThe actual code does
A file src/config/spc.config.ts holds "window size, sigma multiplier, USL policy." This file does not exist. SPC constants live inline in src/spc/*.ts (e.g. D2_CONSTANT, K_SIGMA_MULTIPLIER in controlChart.ts/driftDetection.ts) or are passed as per-call options (SpcEngineOptions, usl).
Control limits use "a window of the last N builds, N configurable — default 25." The production SPC path (computeSpcReport called with loadTelemetryHistory()) uses the entire history — expanding, unbounded, no default window at all. The only 15-build trailing window that exists (DEFAULT_TRAILING_WINDOW_SIZE = 15) is in src/spc/experimentAnalysis.ts, used only for Experiment A's comparative analysis.
"The Rule Evaluator implements four Nelson rules" in a file called westernElectricRules.ts. There are two separate, correctly-named rule files: westernElectricRules.ts (the 4 classic Western Electric rules) and a separate nelsonRules.ts (all 8 Nelson 1984 rules — a superset). Both are wired into computeSpcReport(). This is richer than the document describes, not an error — see SPC From Zero.
SPC §8 describes control limits, WECO/Nelson rules, and Cpk. Two additional detectors exist that §8 never mentions: regressionSpikeDetection.ts (a same-build spike detector) and driftDetection.ts (a two-sided CUSUM drift detector). Both feed into the gate.
Files named telemetryCollector.ts / telemetryWriter.ts; scanner named axeScanner.ts. Actual filenames are src/telemetry/collector.ts, src/telemetry/writer.ts, and src/utils/accessibilityScanner.ts. Formulas and behavior match the document; only the filenames differ.
Appendix B describes an spc-summary.json aggregate artifact in telemetry/aggregated/. No code anywhere writes a file with that name. The one file scripts/run-quality-gate.ts actually writes into telemetry/aggregated/ is gate-verdict.json; the dashboard generator separately writes dashboard-data.json there. Both are git-ignored and regenerated on demand.
Technical explanation

None of these are correctness bugs — every regression-guard script (verify:spc, verify:gates, verify:experiment, verify:stable-cohort, verify:ci, verify:dashboard) passes against the code as it actually exists. They are drift between an early planning document and the implementation that followed it, which is completely normal in real software projects — and a reviewer who spots one of these differences is testing whether you understand your own repository or only your own document.
