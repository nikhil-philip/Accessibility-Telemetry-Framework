Layer 1

CI/CD: The GitHub Actions Workflow

One workflow file, one job, eighteen steps. It doesn't compute anything itself — it sequences every other layer and turns the gate's verdict into a real merge-blocking status check.

Triggers

File: .github/workflows/accessibility-ci.yml. Workflow name: "Accessibility Quality Gate".

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch: {}

concurrency:
  group: accessibility-ci-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read
  • push to main only.
  • pull_request targeting main only.
  • workflow_dispatch — manual trigger, for the reviewer demo (see Reviewer Demo).
  • Concurrency: a new push cancels any still-running run on the same ref, so evidence never accumulates from a stale run.
  • Permissions: read-only. The workflow's own comment: "this workflow never pushes, comments, or deploys; it only reads the checked-out repo and uploads artifacts."

One job, accessibility-quality-gate ("Scan, analyze, and gate"), ubuntu-latest, 20-minute timeout.

Step 11 (verify dashboard) is deliberately placed before step 12 (the scan), because verify-dashboard.ts asserts the 4 originally-committed production telemetry records are still exactly present and byte-identical — a check that would be invalidated if the scan had already appended a new record first.

The gate step's pass/fail genuinely determines the job's overall status — the downstream always() steps produce evidence, they do not rescue a failed job.

What Happens When the Gate FAILS

Beginner explanation

If the gate says FAIL, the CI job genuinely fails — that's what blocks the merge. But the pipeline doesn't just stop and leave you with nothing to look at. It keeps going long enough to build the dashboard and package up all the evidence, so whoever is looking at the failed build can immediately see why it failed, instead of just seeing a red X with no explanation.

"if: always()" in Simple English

Technical explanation

By default, a GitHub Actions job stops running further steps once one step fails. if: always() on a step overrides that — it tells GitHub Actions "run this step regardless of whether an earlier step in this job failed." The workflow's own comment is explicit about why this is safe and not a way of hiding the failure:

# ---------------------------------------------------------------
# Everything from here on runs with `if: always()`. This is a
# deliberate, explained exception to "don't use continue-on-error /
# don't hide failures": the job's overall status is already FAILED
# by the gate step above if the gate returned FAIL, and nothing
# below can undo that. These steps exist so a blocked build still
# produces the dashboard/telemetry evidence an engineer needs to
# see *why* -- not to mask the failure.
# ---------------------------------------------------------------

Note also what the workflow deliberately does not use: continue-on-error does not appear anywhere in the file. The gate step is allowed to genuinely fail the job; if: always() on later steps is the only mechanism used to still produce evidence.

Artifact-Only Evidence, Never Committed Back

permissions: contents: read at the top of the workflow makes a write-back structurally impossible even if a step tried.
- name: Upload quality evidence (dashboard, telemetry, gate verdict, reports)
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: quality-evidence-${{ github.run_id }}
    path: |
      dashboard/
      telemetry/aggregated/
      telemetry/history/
      reports/
    if-no-files-found: warn
    retention-days: 30

See Telemetry → Why Is CI-Generated Telemetry Artifact-Only? for the full reasoning.
