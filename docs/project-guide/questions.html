Basic

Q1. What did you build?

What the reviewer is testingWhether you can summarize your own project without reading source code.
Answer I should give"A framework that scans a demo shopping site for accessibility problems on every build, tracks the defect score over time using Statistical Process Control, and uses that statistical signal to automatically decide whether a build is safe to merge."
Technical follow-up"What's the one number the whole system is built around?"
Answer to follow-up"defectScore — a severity-weighted sum, 10 points per critical violation, 5 per serious, 2 per moderate, 1 per minor, computed once per build in src/telemetry/collector.ts."

Q2. What problem does this solve that existing tools don't?

What the reviewer is testingWhether you understand your own research contribution, not just the implementation.
Answer I should give"Existing tools like axe CLI integrations, pa11y-ci, or Lighthouse CI accessibility budgets all use static threshold gating — fail if the count exceeds a fixed number. That can't tell a one-off blip from a sustained regression, and it's blind to slow, creeping degradation across many builds. My framework treats the defect count as a process to be monitored statistically, not just measured once."
Technical follow-up"Is that a novel statistical method?"
Answer to follow-up"No — SPC itself is a well-established manufacturing discipline. My contribution is the bridge between SPC/software-quality engineering and automated WCAG accessibility testing specifically, which isn't a solved or common practice, per ARCHITECTURE.md §9."

Q3. What's the difference between axe-core and your framework?

What the reviewer is testingWhether you understand you built infrastructure around a tool, not a competitor to it.
Answer I should give"axe-core is the rule engine that actually detects individual WCAG violations on a page — I didn't write that, Deque did, and I use it exactly as-is via @axe-core/playwright. My framework is everything around it: turning many scans into a measured process, applying SPC, and gating CI on the result."
Technical follow-up"Where exactly does axe-core get invoked?"
Answer to follow-up"One place only: createAxeBuilder() in src/utils/accessibilityScanner.ts, which is the single constructor for AxeBuilder used everywhere, configured with the WCAG tags from src/config/axe.config.ts."

Q4. Who is the intended user of this system?

What the reviewer is testingWhether the design decisions map to a real audience.
Answer I should give"A development team's quality engineer or accessibility lead — someone who wants CI to automatically block genuine regressions without needing to manually eyeball every scan result, and who wants a dashboard they can point to as evidence during an accessibility audit."
Technical follow-up"Does an individual developer get any feedback, or only the team lead?"
Answer to follow-up"The gate verdict becomes a required PR status check, so any developer opening a PR sees PASS/WARN/FAIL directly on their own pull request — plus GitHub Actions annotations from ciAdapter.ts pointing at the specific triggered reasons."

Architecture

Q5. Walk me through what happens when a build runs.

What the reviewer is testingWhether you actually know the pipeline, not just the marketing summary.
Answer I should giveSee the full 12-step walkthrough on Architecture → One Build, File by File — rehearse it until you can say it without looking, naming real files (reporter.ts, collector.ts, writer.ts, spcEngine.ts, qualityGateEvaluator.ts, ciAdapter.ts) at each step.
Technical follow-up"How does a Playwright test's axe result actually reach the telemetry writer?"
Answer to follow-up"Each test attaches its raw axe result as a Playwright attachment named axe-results. A custom reporter, TelemetryReporter in src/telemetry/reporter.ts, collects every attachment across the whole run in onTestEnd(), then in onEnd() calls collectTelemetry() once and writes a single record."

Q6. Why seven layers instead of fewer?

What the reviewer is testingWhether the layering was a deliberate design choice or accidental complexity.
Answer I should give"Each layer has exactly one job, and each boundary is a real file on disk, not just a mental separation. That's what lets me test the statistics engine, the gate engine, and the dashboard's data layer completely independently of a running browser — which is exactly what the six verify:* scripts do."
Technical follow-up"Give a concrete example of that independence."
Answer to follow-up"verify:spc constructs synthetic number series by hand and checks that each SPC rule fires correctly — it never launches Playwright or touches ShopSmart at all."

Q7. Why file boundaries (JSON on disk) between layers instead of function calls?

What the reviewer is testingWhether you understand the trade-off, not just the choice.
Answer I should give"It gives me a full audit trail for free — every intermediate state is inspectable JSON, which matters a lot for a dissertation's evaluation evidence. The cost is that it doesn't scale to huge volumes the way a real database would, which ARCHITECTURE.md §9 names directly as a threat to validity."
Technical follow-up"What would you use instead at real production scale?"
Answer to follow-up"A proper time-series store — ARCHITECTURE.md §7 names SQLite/Postgres as the considered alternative, rejected only because it adds infrastructure this dissertation's scope doesn't need."

Q8. What's the actual difference between L5 (SPC) and L6 (Gate)?

What the reviewer is testingWhether you can separate "detect a signal" from "decide what to do about it."
Answer I should give"L5 detects every statistically interesting pattern it can — twelve separate rule evaluations plus trend, spike, drift, and capability — and reports all of them. L6 is the only layer that decides which of those patterns matter enough to fail a build versus just warn about it. That decision lives entirely in one declarative policy object, gatePolicies.ts."
Technical follow-up"Could you change the policy without touching the SPC engine?"
Answer to follow-up"Yes — that's the whole point of keeping policy as data. Tightening maxSeriousDefects from 5 to 3 is a one-line change in gatePolicies.ts and touches nothing in src/spc/."

Accessibility

Q9. What WCAG level do you test against?

What the reviewer is testingBasic factual knowledge of your own configuration.
Answer I should give"AA — src/config/axe.config.ts fixes WCAG_LEVEL = 'AA', and scans use the tag set wcag2a, wcag2aa, wcag21aa, wcag22aa, best-practice."
Technical follow-up"Why include best-practice, which isn't a WCAG level at all?"
Answer to follow-up"Five of the 24 seeded violation rules in the ShopSmart catalog — heading-order, landmark-one-main, region, tabindex, aria-dialog-name — carry no WCAG success-criterion tag at all; they're axe-core best-practice-only rules. Dropping that tag would silently omit them from every scan."

Q10. Why axe-core over Lighthouse or pa11y?

What the reviewer is testingWhether the tool choice was justified or arbitrary.
Answer I should give"axe-core is Deque's actively-maintained, de facto industry-standard rule engine with configurable WCAG tags, and it has an official Playwright binding. pa11y has thinner rule coverage, and Lighthouse treats accessibility as a secondary concern that's harder to isolate from its other audits." (ARCHITECTURE.md §7.)
Technical follow-up"Did you evaluate this empirically, or is it a documented preference?"
Answer to follow-up"It's a documented, reasoned choice in the architecture document, not an empirical head-to-head comparison run as part of this project — that's an honest limitation, not something I measured."

Q11. How do you know your seeded ShopSmart violations are realistic?

What the reviewer is testingWhether the test fixture is grounded in something real or just made up.
Answer I should give"They're documented in a ground-truth catalog, docs/violations/catalog.json, with 24 real axe-core rule IDs and 81 individual instances, each with a WCAG criterion, impact level, and remediation note — and each build's manifest records the actual axe-measured count alongside the catalog's expected count, so I can cross-check the real scanner against my own answer key."
Technical follow-up"Does the catalog say 81 or 80?"
Answer to follow-up"Honestly — the catalog's own prose in catalog.md says 80, but counting instanceId entries directly in catalog.json gives 81. That's a real off-by-one in the project's own documentation, and I'd rather say that plainly than repeat the wrong number."

Q12. What pages does the framework scan?

What the reviewer is testingBasic factual recall.
Answer I should give"Eight ShopSmart pages, listed in src/config/sites.config.ts: Login, Dashboard, Product Listing, Product Details, Shopping Cart, Checkout, User Profile, and Contact Us. Four of them require an authenticated session."
Technical follow-up"How does authentication work for the ones that need it?"
Answer to follow-up"tests/auth.setup.ts is a Playwright setup project that logs in once and saves storageState to playwright/.auth/user.json, which authenticated-page fixtures reuse without logging in per test."

Telemetry

Q13. What is defectScore and why weighted?

What the reviewer is testingWhether you understand the one number everything downstream depends on.
Answer I should giveSee Telemetry → What Is defectScore? — 10×critical + 5×serious + 2×moderate + 1×minor, so one critical violation isn't statistically invisible next to ten minor ones.
Technical follow-up"Were these specific weights validated empirically?"
Answer to follow-up"No — they mirror a common severity-weighted defect-density convention from software quality engineering, documented in ARCHITECTURE.md §8.2, but not tuned against ShopSmart's own violation distribution. That's an honest, named limitation."

Q14. Why append-only telemetry?

What the reviewer is testingWhether the data-integrity design was intentional.
Answer I should give"So the history the SPC engine reasons over can never be silently rewritten. writeTelemetryRecordTo() in src/telemetry/writer.ts never overwrites an existing file — on a filename collision it appends a numeric suffix instead."
Technical follow-up"How is that actually enforced, not just documented?"
Answer to follow-up"There's exactly one fs.writeFileSync call against telemetry/history/ anywhere in src/ — the one in writer.ts. No other code path in the whole source tree touches that directory."

Q15. Why is CI-generated telemetry artifact-only?

What the reviewer is testingWhether the CI design avoids a common anti-pattern (bots pushing commits).
Answer I should giveSee Telemetry → Why Artifact-Only — the workflow declares permissions: contents: read and has no git push step anywhere; new telemetry only leaves the runner as a 30-day upload-artifact.
Technical follow-up"So how does the committed 4-record baseline ever grow?"
Answer to follow-up"Only when a human deliberately downloads a real telemetry record and commits it — the same way the current 4 baseline builds got there. That's a manual, curated step, not automatic."

Q16. What's the difference between telemetry/history and telemetry/experiments?

What the reviewer is testingWhether you can tell real evidence apart from validation fixtures.
Answer I should giveSee Telemetry → Production vs. Experiments — history is 4 real scans; experiments are two 30-record synthetic, seeded cohorts built to exercise the SPC engine under known conditions.
Technical follow-up"Does the gate ever run against the experiment data in production?"
Answer to follow-up"No — evaluateFromDisk(), the function CI actually calls, only reads telemetry/history/. The experiment cohorts are read separately, only by the experiment-analysis tooling and the dashboard's Experiment A/B panels."

SPC

Q17. Why SPC instead of a simple threshold?

What the reviewer is testingThe core research justification.
Answer I should give"A threshold can't distinguish a one-off blip from a sustained regression, and it's structurally blind to a slow drift where every individual build looks fine. SPC gives me control limits derived from the process's own recent behavior, plus pattern rules that catch multi-build trends a single threshold check never could."
Technical follow-up"Give a concrete case where SPC and a threshold would disagree."
Answer to follow-up"Nelson Rule 3 (6 consecutive trending builds) or the CUSUM drift detector can flag a build whose individual score is still well under any fixed threshold, because the concern is the direction over time, not the single value."

Q18. Why an I-MR chart specifically?

What the reviewer is testingChart-selection reasoning, not just chart usage.
Answer I should give"Builds arrive one at a time, not in natural subgroups of several samples per time point — that's exactly the situation an Individuals-Moving-Range chart is designed for, as opposed to an X̄-R chart, which needs subgroups."
Technical follow-up"How is sigma estimated without subgroups?"
Answer to follow-up"From the moving range between consecutive individual points: σ̂ = MR̄ / 1.128, where 1.128 is the standard d2 constant for a subgroup size of 2."

Q19. What's the difference between the Western Electric and Nelson rule sets?

What the reviewer is testingWhether you know your implementation exceeds what ARCHITECTURE.md originally described.
Answer I should give"Western Electric is 4 classic rules; Nelson (1984) is a superset of 8, adding alternating-pattern, strict-trend, tight-clustering, and mixture detection. Both are implemented in separate files and both run on every build — westernElectricRules.ts and nelsonRules.ts."
Technical follow-up"Which ones actually affect the gate's PASS/WARN/FAIL decision?"
Answer to follow-up"Only Rule 1 from each set is wired to FAIL. Every other triggered rule from either set defaults to WARN via warnOnOtherTriggeredRules: true."

Q20. What's the difference between a control-limit violation and WECO/Nelson Rule 1?

What the reviewer is testingAttention to a genuine overlap in the implementation.
Answer I should giveSee SPC → Control-Limit Violations — they're testing the same underlying "beyond 3σ" event, computed two different ways: a direct numeric comparison against UCL/LCL versus a generic pattern-matching call. Both are wired to FAIL.
Technical follow-up"Isn't that redundant?"
Answer to follow-up"Functionally, largely yes — but keeping them as separate signals in the gate's reason list keeps the output honest about why it fired, and the direct comparison is also what the chart itself needs internally, independent of the rule evaluators."

Q21. Why CUSUM in addition to the pattern rules?

What the reviewer is testingWhether you understand CUSUM's specific statistical advantage.
Answer I should give"CUSUM accumulates small deviations over time, so it's specifically more sensitive than Shewhart-style pattern rules to a small, persistent shift that never individually crosses a sigma boundary but adds up."
Technical follow-up"What are the k and h constants, and are they tuned?"
Answer to follow-up"k = 0.5σ̂ (allowed slack), h = 5σ̂ (alarm threshold) — the textbook-standard tabular CUSUM defaults, not empirically tuned against this project's own telemetry. Honest limitation, not a hidden claim."

Experiments

Q22. Why do you need synthetic experiments at all?

What the reviewer is testingWhether the synthetic data is a crutch or a deliberate methodology.
Answer I should give"Real production history is only 4 builds — nowhere near enough to prove an SPC methodology works, or to exercise scenarios like a 5-phase regime change or a stable capability study. Synthetic, seeded, reproducible cohorts let me validate the engine against known-correct conditions I control."
Technical follow-up"Are they clearly separated from real evidence?"
Answer to follow-up"Yes — different directories (telemetry/experiments/ vs. telemetry/history/), different generators, and the gate's evaluateFromDisk() only ever reads real history, never the experiment cohorts."

Q23. What does Experiment A actually prove?

What the reviewer is testingWhether you can state a concrete, falsifiable result, not just "it worked."
Answer I should give"That expanding-history and trailing-window SPC analysis genuinely behave differently under changing conditions — expanding history let one early outlier (build 1) permanently distort Rule 1 for the back half of the cohort, while a 15-build trailing window eventually let that old point age out. Both are real, verified results: 1 PASS/3 WARN/26 FAIL for expanding, 1 PASS/5 WARN/24 FAIL for trailing."
Technical follow-up"Which method is 'better'?"
Answer to follow-up"Neither, unconditionally — that's the point. Expanding history has more statistical power early on; trailing windows stay current but discard old evidence. It's a genuine trade-off the experiment makes visible with real numbers."

Q24. What does Experiment B actually prove?

What the reviewer is testingWhether you understand its narrower, specific purpose.
Answer I should give"That the Cpu/Cpk capability formula computes correctly and produces a sensible, verifiable result (Cpu ≈ 2.9811, USL=40) when its stability assumption is actually satisfied — a single, deliberately stationary regime."
Technical follow-up"Does it prove ShopSmart itself is capable?"
Answer to follow-up"No — it proves the capability math and its integration with the SPC/gate engine work correctly on synthetic data. It says nothing about the real ShopSmart application's actual capability, which would need a much longer real production history."

Q25. Why is the regression injected exactly at build 23?

What the reviewer is testingWhether the experiment design is arbitrary or deliberate.
Answer I should give"Build 23 is the first build of Phase D ('Deliberate regression'), which runs builds 23–25 — placed after a full 7-build stable Phase C (16–22) specifically so the regression stands out clearly against a genuinely quiet baseline, not a noisy one."
Technical follow-up"Does the real data actually show the jump, or is it just a documented intention?"
Answer to follow-up"It's in the real generated files: defectScore goes from 7 at build 22 to 46 at build 23 — a genuine step-change, and the regression-spike detector correctly fires exactly there."

Quality Gates

Q26. How does the gate decide PASS/WARN/FAIL?

What the reviewer is testingWhether you know the exact derivation logic.
Answer I should giveSee Quality Gates → PASS, WARN, FAIL — any FAIL reason makes the whole verdict FAIL; otherwise any WARN reason makes it WARN; otherwise PASS.
Technical follow-up"Name every check that can independently produce a FAIL."
Answer to follow-up"Any critical defect, more than 5 serious defects, defectScore ≥50, an SPC control-limit violation, WECO or Nelson Rule 1, a detected regression spike, or Cpu <1.0."

Q27. Why doesn't WARN block CI?

What the reviewer is testingWhether the two-tier severity model is justified.
Answer I should giveSee Quality Gates → Why WARN Doesn't Block — WARN is for signals worth a human noticing, not signals severe enough to stop the whole team; if it blocked, it would be identical to FAIL.
Technical follow-up"Is a WARN visible anywhere, or does it just disappear?"
Answer to follow-up"It's fully visible — the gate step still exits 0, but the reason still appears in the console output, the GitHub Actions annotations, the step summary, and the dashboard's reasons list."

Q28. Why is policy separate from ciAdapter.ts?

What the reviewer is testingSeparation-of-concerns understanding.
Answer I should giveSee Quality Gates → Why ciAdapter Has No Policy — ciAdapter.ts imports only the GateVerdict type and contains zero threshold literals; it's pure formatting.
Technical follow-up"What's the practical benefit?"
Answer to follow-up"A policy change never requires touching CI plumbing, and ciAdapter.ts can be unit-tested with hand-built verdict fixtures — verify-ci.ts does exactly that, without a real telemetry/history/ or a real CI environment."

Q29. What happens when some rules say WARN and others say FAIL on the same build?

What the reviewer is testingEdge-case understanding of the derivation logic.
Answer I should give"FAIL wins outright — deriveStatus() checks for any FAIL reason first. The verdict's reasons array still lists every triggered reason, WARN and FAIL alike, so nothing is hidden even though the overall status collapses to the worst one."
Technical follow-up"Does the number of FAIL reasons matter, or is one enough?"
Answer to follow-up"One is enough — reasons.some(r => r.severity === 'FAIL') is a boolean check, not a count. Ten FAIL reasons and one FAIL reason both just produce status: 'FAIL'."

CI/CD

Q30. Walk me through the workflow triggers.

What the reviewer is testingFactual recall of the actual YAML.
Answer I should give"Push to main, pull requests targeting main, and manual workflow_dispatch — plus a concurrency group that cancels an in-progress run on the same ref when a new one starts."
Technical follow-up"Why cancel in-progress runs?"
Answer to follow-up"So evidence never accumulates from a stale run that's about to be superseded — if you push again quickly, you don't want two runs racing to upload conflicting artifacts."

Q31. What happens when the gate step fails?

What the reviewer is testingWhether you understand if: always() vs. hiding failures.
Answer I should giveSee CI/CD → What Happens When the Gate FAILS — the job genuinely fails, but four downstream steps still run because they're marked if: always(), so evidence is still produced.
Technical follow-up"Does the workflow use continue-on-error anywhere?"
Answer to follow-up"No — I checked the full file specifically for that; it doesn't appear anywhere. The gate step is allowed to genuinely fail the job; if: always() on later steps is the only mechanism used."

Q32. Why is CI permissions read-only?

What the reviewer is testingSecurity-conscious design awareness.
Answer I should give"permissions: contents: read at the top of the workflow means it structurally cannot push, comment, or deploy — even if a future edit accidentally added a git command, it would fail without a credentials change most contributors wouldn't casually make."
Technical follow-up"Does anything in the workflow need write access at all?"
Answer to follow-up"No — every output (dashboard, telemetry, gate verdict, reports) leaves only via actions/upload-artifact@v4, which doesn't require write access to repository contents."

Q33. What is if: always() doing, in plain terms?

What the reviewer is testingWhether you can explain a GitHub Actions mechanism in beginner language.
Answer I should giveSee CI/CD → if: always() in Simple English — it tells GitHub Actions "run this step regardless of whether an earlier step in this job already failed."
Technical follow-up"Doesn't that risk hiding the failure?"
Answer to follow-up"No — the job's overall status is already FAILED by the gate step, and nothing downstream can undo that. The workflow's own comment says this explicitly: these steps exist to produce evidence for a blocked build, not to mask the block."

What the reviewer is testingBasic factual recall.

What the reviewer is testingWhether "presentation only" is enforced, not just claimed.

Research Methodology

Q38. What is your research contribution?

What the reviewer is testingWhether you can state it precisely, the way a dissertation committee expects.
Answer I should givePer ARCHITECTURE.md §9: four contributions — C1 the reference framework/architecture itself, C2 a defined method for turning raw axe output into an SPC-suitable measurement, C3 a declarative, statistically-grounded gate policy as an alternative to static-threshold gating, and C4 the empirical telemetry/experiment dataset itself as evaluation evidence.
Technical follow-up"Is any of this a novel statistical algorithm?"
Answer to follow-up"No, and I wouldn't claim it is. The positioning, stated directly in the architecture document, is the bridge between two established fields — accessibility engineering and SPC/software-quality engineering — not a novel algorithm in either one alone."

Q39. What are your research questions?

What the reviewer is testingWhether the experiments map back to stated questions.
Answer I should give"RQ1: can I-MR charts with a severity-weighted score meaningfully model accessibility-violation variation across builds? RQ2: does an SPC-informed gate reduce false positives/negatives relative to a static-threshold gate on the same history? RQ3: which distributional assumptions actually hold for this kind of telemetry, and does the weighted-score transform help?"
Technical follow-up"Which of these are actually answered by what you built, versus still open?"
Answer to follow-up"Experiments A and B give real, verifiable evidence toward RQ1 — the methodology genuinely works and produces sensible, reproducible numbers. RQ2 and RQ3 are only partially addressable with 4 real builds; a fuller answer needs real production history I don't have yet. That's honestly still open." (See Tough Questions for more on this.)

Q40. With only 4 real builds, how would you even evaluate RQ2 (false positive/negative reduction)?

What the reviewer is testingWhether you'll overclaim or answer honestly.
Answer I should give"Honestly, not fully — not yet. What I can show is that the methodology behaves correctly and sensibly on controlled synthetic data with known ground truth (Experiment A's known regression, known stable phases). A rigorous RQ2 answer needs a real, much longer production history to compare SPC-gated outcomes against a static-threshold baseline on the same real data — that's future work, not something this dissertation's timeline could produce."
Technical follow-up"So is RQ2 currently unanswered?"
Answer to follow-up"Partially answered on synthetic data, genuinely open on real data. I'd rather say that plainly than imply otherwise."

Q41. Is this reproducible by someone else?

What the reviewer is testingBasic scientific reproducibility standards.
Answer I should give"Yes for the synthetic experiments — both generators use a fixed numeric seed, and verify-experiment.ts/verify-stable-cohort.ts explicitly check that the same seed produces byte-identical output. The real ShopSmart scans are also reproducible in the sense that anyone can clone the repo, run npm run test:a11y, and get a real new telemetry record from the same deterministic demo app."
Technical follow-up"What isn't guaranteed to reproduce exactly?"
Answer to follow-up"timestamp, buildId, and commitSha in a freshly-generated telemetry record will differ by definition (they're derived from the current time/git state), but the violation content and defectScore for a fixed ShopSmart build should reproduce, since the app itself is static and deterministic."

Security

Q42. Does this project handle any real user data or credentials?

What the reviewer is testingWhether you understand your own attack surface.
Answer I should give"No — ShopSmart's login and cart are simulated, with no real backend or persistence; the demo app is a static site with fixed demo data. There's no real payment, no real personal data, no real authentication against an external identity provider."
Technical follow-up"What does auth.setup.ts actually authenticate against, then?"
Answer to follow-up"ShopSmart's own simulated login flow — it saves Playwright's storageState so authenticated-page tests don't need to repeat a fake login, not a credential against any real identity system."

Q43. What's the security posture of the CI workflow itself?

What the reviewer is testingWhether CI hardening was considered.
Answer I should give"permissions: contents: read at the workflow level — the most restrictive setting that still allows checkout and artifact upload. No secrets are referenced anywhere in the workflow file, and nothing it does requires write access to the repository."
Technical follow-up"Does verify-ci.ts check for anything security-relevant?"
Answer to follow-up"It checks for failure-hiding patterns like || true or continue-on-error: true — not a security scan per se, but it does guard against the workflow silently swallowing a real failure, which is a related integrity concern."

Reproducibility

Q44. Can I regenerate the experiments and get the same result?

What the reviewer is testingWhether reproducibility is a tested property, not an assumption.
Answer I should give"Yes — npm run generate:experiment and npm run generate:stable-cohort use fixed seeds (20260815 and 71430901), and both verify-experiment.ts and verify-stable-cohort.ts include an explicit reproducibility check: same seed produces byte-identical JSON twice; seed+1 produces a genuinely different sequence."
Technical follow-up"Why bother checking seed+1 produces something different?"
Answer to follow-up"To rule out a broken generator that ignores its seed entirely and just always produces the same output regardless of input — that would make the 'reproducibility' claim vacuous."

Q45. What happens if I run the pipeline on a different OS?

What the reviewer is testingEnvironment-dependency awareness.
Answer I should give"CI runs on ubuntu-latest; I developed locally on Windows. The telemetry reporter actually has a specific Windows accommodation — it tries several hardcoded Git install paths as a fallback, because some Windows shells don't expose git on PATH for spawned child processes even when it's installed."
Technical follow-up"Could that fallback list ever be wrong on someone else's machine?"
Answer to follow-up"Yes, honestly — it's a small, named list of common Windows Git install locations, not an exhaustive PATH resolution. On a machine with Git installed somewhere unusual, commitSha/branch would fall back to 'unknown' rather than crash, which is a safe failure mode but not a fully general one."

Limitations

Q46. What's the biggest limitation of this project?

What the reviewer is testingWhether you'll name a real limitation unprompted.
Answer I should give"Only 4 real production telemetry records exist. Every claim about the SPC methodology actually working is currently backed by synthetic, seeded data with known ground truth — which proves the machinery is correct, but doesn't yet prove it behaves usefully on the messy, unpredictable variation a real long-running project would produce."
Technical follow-up"What would fix that?"
Answer to follow-up"Time — running the real CI pipeline against real ShopSmart changes for months, accumulating real telemetry, and only then evaluating RQ2/RQ3 against that history."

Q47. Is 30 synthetic builds enough to validate SPC methodology?

What the reviewer is testingStatistical rigor / sample-size awareness.
Answer I should give"It's enough to demonstrate the mechanics work correctly and produce sensible, checkable numbers — which is what Experiments A and B actually set out to do. It is not enough to make a strong statistical claim about long-run false-positive/false-negative rates; that needs a much larger sample, ideally real data. I'd call this a methodology validation, not a statistical power study."
Technical follow-up"Why 30 specifically, then?"
Answer to follow-up"Large enough to give the 15-build trailing window room to actually differ from expanding history for half the cohort, and to fit five distinct 3-to-8-build phases without any phase being too short to establish its own character."

Difficult

Q49. If WCAG rules change, does your framework need to change?

What the reviewer is testingWhether the design anticipated an external dependency changing.
Answer I should give"Not structurally — the WCAG tag set is one config array in src/config/axe.config.ts, and axe-core itself (a third-party dependency) is what actually tracks rule changes. Updating the tag list or bumping the @axe-core/playwright version wouldn't touch the SPC engine, the gate, or the dashboard at all — they operate on the resulting defectScore, not on individual rule identities."
Technical follow-up"Would old telemetry records become incomparable to new ones after a rule-set change?"
Answer to follow-up"Potentially, yes — that's a real, honest edge case. If new rules start firing that never could before, defectScore could jump for reasons unrelated to any real regression, and the SPC engine has no way to know the measurement definition itself changed. That's a genuine limitation worth naming, not something the framework currently detects or compensates for."

Q50. Isn't 4 real builds too small to trust any of this?

What the reviewer is testingWhether you'll defend an indefensible claim or concede honestly.
Answer I should give"You're right to push on that, and I won't claim otherwise — 4 builds cannot validate a statistical methodology on their own. What they validate is that the pipeline runs correctly end-to-end on real data: real axe-core output really does become a real telemetry record, really does flow through the real SPC engine and gate. The statistical validation itself is carried by the synthetic experiments, which is a real limitation of scope, not a hidden one."
Technical follow-up"So what's actually proven versus assumed?"
Answer to follow-up"Proven: the pipeline works end-to-end, the math is implemented correctly (per the verify scripts), and the methodology behaves sensibly on controlled data. Assumed, not yet proven: that this specific methodology, with these specific weights and thresholds, will behave usefully on a real, messy, multi-month accessibility history."

Q51. What's stopping someone from gaming the defect score?

What the reviewer is testingAdversarial/robustness thinking.
Answer I should give"Honestly, not much at the framework level — a developer could disable a rule in axe.config.ts, or narrow sites.config.ts's route list, and the score would drop without any real accessibility improvement. That's true of essentially any automated quality gate: it measures what it's configured to measure, and changing the configuration changes the measurement."
Technical follow-up"Is there any safeguard against that at all?"
Answer to follow-up"Only an organizational one, not a technical one: config changes go through the same PR review and version control as any other code change, so a route or rule being quietly removed would show up in a diff. There's no automated detection of 'the measurement definition itself just changed' — that's a real gap, not a solved problem."
