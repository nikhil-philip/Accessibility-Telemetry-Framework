What This Guide Is For

This is a plain-English guide to the Accessibility Telemetry Framework — the project in accessibility-telemetry-framework/ — written so you (the author) can explain what you built, why you built it, and defend it in a viva, without needing to re-read the TypeScript source. Every claim in this guide was checked directly against the repository's code, configuration, git history, and real generated data — not against memory or assumption. Where the code disagrees with the project's own architecture document, that disagreement is called out honestly rather than hidden.

If the reviewer asks: "What did you build?"

The 30-second answer

What I should say

"I built a system that runs automated accessibility tests on a demo shopping website every time code changes, but instead of just saying 'pass' or 'fail' on one test run, it treats the accessibility defect count as a manufacturing-style measurement and tracks it over time using Statistical Process Control — the same discipline factories use to detect when a machine is drifting out of calibration. A quality gate then uses that statistical signal, not just a raw count, to decide whether a build is safe to merge, and a dashboard shows the evidence."

The 60-second answer

What I should say

"Most accessibility CI tools ask one narrow question: does this build violate a WCAG rule, yes or no? They compare a violation count against a fixed threshold. My project asks a different question: is the application's accessibility quality stable, improving, or quietly getting worse over many builds? I run Playwright with axe-core against a demo e-commerce app called ShopSmart, turn each scan into a single severity-weighted defect score, and store one record per build as telemetry. Then I run that score series through an Individuals–Moving-Range control chart — the same statistical method used to monitor manufacturing processes — with Western Electric and Nelson pattern rules, a CUSUM drift detector, and a regression-spike detector layered on top. A declarative quality gate turns those statistical signals into PASS, WARN, or FAIL, and that verdict becomes a required GitHub Actions status check. A static dashboard displays everything — it doesn't calculate anything itself, it only reads what the SPC engine and the gate already decided."

The 3-minute answer

What I should say

"The core idea is borrowed from manufacturing quality engineering. In a factory, you don't reject a part just because one measurement is slightly off — you watch the process over time and distinguish ordinary variation from a real problem. I apply that same idea to accessibility defects in a CI pipeline.

Concretely: every time the pipeline runs, Playwright drives a browser through eight pages of a demo shopping site (ShopSmart) that I built specifically to have known, cataloged accessibility defects. axe-core scans each page against WCAG 2.2 A/AA rules. I turn the violations into one number per build — a severity-weighted defect score, critical defects worth 10 points, serious worth 5, moderate worth 2, minor worth 1 — and write it as an immutable JSON telemetry record.

That score becomes one point on an I-MR control chart. I compute the center line, the moving range, and 3-sigma control limits from the build history, then run two families of pattern-detection rules against it — the four classic Western Electric rules and all eight Nelson rules — plus a regression-spike detector and a CUSUM drift detector for slow degradation the point-by-point rules can miss. If there's an agreed upper specification limit, I also compute Cpu, a process-capability index, but only on a cohort I can prove is a single stable regime — I built two separate experiments specifically to keep that assumption honest.

All of those signals feed a declarative quality gate — a policy object, not scattered if-statements — that returns PASS, WARN, or FAIL. That verdict is wired into a real GitHub Actions workflow as the thing that decides whether a build can merge. A generated static dashboard then displays the control chart, the gate verdict, and both experiments' results, without doing any of its own math — it's a pure presentation layer over numbers the SPC and gate engines already computed. The whole thing is my BITS Pilani M.Tech final-year dissertation project, and its research contribution is the bridge between two established fields — WCAG accessibility automation and SPC/software-quality engineering — not a new algorithm in either one."

Why This Project Exists

Off-the-shelf accessibility CI tools (axe CLI integrations, pa11y-ci, Lighthouse CI accessibility budgets) all use static threshold gating: a build fails if a fixed violation count is exceeded, full stop. That approach cannot tell the difference between a one-off blip (a third-party widget's markup shifted slightly) and a genuine, sustained regression. It also can't see a slow accessibility-debt creep — eight builds in a row that each look individually "fine" but are all trending the same direction.

This project's contribution, as stated in docs/architecture/ARCHITECTURE.md §9, sits at the intersection of two already-established fields — WCAG accessibility automation and SPC / software quality engineering — and its value is the bridge between them, not a novel algorithm in either field alone.
