Statistical Process Control, From Zero

You do not need a statistics background to defend this section — you need to understand seven or eight ideas, in order, and know exactly which file implements each one. This page builds those ideas from scratch, then walks through every detector this project actually runs, one at a time.

The Basics

A "process"

Beginner explanation

A process is anything that happens repeatedly and produces a measurable result each time. A factory machine stamping out metal parts is a process — each part's thickness is a measurement. Here, "run the accessibility tests on ShopSmart" is the process, and each build's defectScore is the measurement.

Variation

Beginner explanation

No process ever produces the exact same measurement twice. Even a perfectly good machine's parts vary by a tiny amount. Even a perfectly good codebase's defect score will wobble slightly build to build (a new page added to the crawl set, a third-party widget's markup shifting). Variation is simply the fact that the numbers move around; SPC's whole job is deciding whether a particular movement is meaningful or not.

Mean (average) and standard deviation ("sigma")

Beginner explanation

The mean is the plain average of a set of numbers — add them up, divide by how many there are. It's "the middle" the process tends to sit around. Standard deviation (written σ, "sigma") is a single number describing how far the measurements typically spread out from that middle. A small sigma means the numbers cluster tightly; a large sigma means they're scattered widely. Sigma is what turns "this build's score is a bit higher" into "this build's score is unusually, suspiciously higher."

Technical explanation

This project does not compute sigma from raw sample variance. Because builds arrive one at a time (not in natural subgroups), it uses the moving range method standard to an Individuals chart: σ̂ = MR̄ / 1.128, where MR̄ is the mean of the absolute differences between consecutive builds, and 1.128 is the d2 control-chart constant for a subgroup size of 2. This is exact code from src/spc/controlChart.ts: export const D2_CONSTANT = 1.128; … const sigma = mrBar / D2_CONSTANT;

Control Limits: UCL, LCL, and the I-MR Chart

The project uses an Individuals–Moving-Range (I-MR) chart, the correct SPC chart family for data that arrives one point at a time rather than in natural groups of several samples.

UCL for the MR chart3.267 × MR̄Flags an unusually large single jump between two consecutive builds.
Beginner explanation

Imagine plotting every build's defect score as a dot on a timeline. Draw a horizontal line through the average (the center line). Draw two more lines above and below it — the UCL and LCL — at a distance chosen so that, if the process really is behaving normally, a dot almost never lands outside them by chance. If a dot does land outside, that's your signal: something about the process itself has probably changed, not just ordinary noise.

Possible reviewer question

"Why 2.6595, not exactly 3?" Because 2.6595 × MR̄ algebraically equals 3 × σ̂ once you substitute σ̂ = MR̄ / 1.128 (3 / 1.128 = 2.6595…). It's the same "3-sigma" limit, expressed directly in terms of the moving range so the code never needs to compute sigma as an intermediate step. src/spc/controlChart.ts even names the constant I_CHART_SIGMA_FACTOR = 3 / D2_CONSTANT to make this explicit.

Common Cause vs. Special Cause, Stable vs. Unstable

TermPlain English
Common cause variationOrdinary, expected noise. The process is "in control" — nothing needs investigating.
Special cause variationA signal that something structurally changed — a real regression, or a real improvement. The process is "out of control" and deserves a human's attention.
Stable processOnly common-cause variation is present; the center line and spread aren't shifting.
Unstable processA special cause has been detected — a rule triggered, a control limit was crossed, a trend or drift was found.
What I should say

"I'm using SPC because I don't want to look at every accessibility result in isolation. I want to know whether the behaviour of the process itself is becoming unusual. A static threshold — 'fail if more than 10 violations' — can't make that distinction. It can't tell a one-off blip from a sustained regression, and it's structurally blind to eight builds in a row that are each individually fine but all drifting the same direction."

Every Detector This Project Actually Runs

All of the following are called, in this order, inside computeSpcReport() (src/spc/spcEngine.ts): control chart → Western Electric rules → Nelson rules → trend → regression spike → drift → capability.

Western Electric Rule 1 (and the other 3 WECO rules)

1. Plain EnglishOne single point is way outside the normal band — a sudden, large jump.
2. Technicalsrc/spc/westernElectricRules.ts: nOfMBeyondSigma(values, centerLine, sigma, k=3, n=1, m=1) — 1 of the last 1 point is ≥3σ from the center line, either side.
3. What it detectsA single build with a dramatically worse (or better) score than the process's usual behavior.
4. Why it mattersIt's the sharpest, most obvious signal — the classic "3-sigma outlier" every SPC course starts with.
5. How this project uses itWECO Rule 1 is one of exactly two rules the gate policy treats as an automatic FAIL (gatePolicies.ts: failRules: [{ruleSet:'WESTERN_ELECTRIC', rule:1}, {ruleSet:'NELSON', rule:1}]).
6. Possible criticismReviewers may ask why WECO Rule 1 and Nelson Rule 1 are both listed separately in the gate policy when they're mathematically identical.
7. How to answer"They are the same pattern test, computed once and referenced from both rule sets — experimentAnalysis.ts even documents that they always agree by construction. Listing both in failRules is defensive/explicit, not double-counting: the gate's reason list would report a single triggered rule either way, since the loop de-duplicates identical outcomes in practice."

Nelson Rule 1 (and the fuller 8-rule Nelson set)

1. Plain EnglishSame idea as WECO Rule 1 — one point wildly outside the band — but evaluated as part of a larger, 8-rule family covering more subtle patterns (long same-side runs, strict trends, alternating zig-zags, and unusually tight clustering).
2. Technicalsrc/spc/nelsonRules.ts — evaluateNelsonRules() runs all 8 Nelson (1984) rules; Rule 1 uses the identical nOfMBeyondSigma(...,3,1,1) call as WECO Rule 1.
3. What it detectsRules 1–6 mirror WECO's escalating-severity pattern; Rule 4 (14 alternating) catches an artificially "too regular" oscillation; Rule 7 (15 within 1σ) catches suspiciously low variation (possible measurement problem); Rule 8 (8 beyond 1σ, mixed both sides) catches a mixture of two different underlying processes.
4. Why it mattersNelson's rules are a strict superset of WECO's — implementing both gives more pattern coverage without changing the underlying math.
5. How this project uses itOnly Nelson Rule 1 is wired to FAIL the gate by default; any of the other 7, if triggered, falls under warnOnOtherTriggeredRules: true and produces a WARN.
6. Possible criticism"Why implement 12 total rule evaluations (4 WECO + 8 Nelson) when only 2 of them ever produce a FAIL?"
7. How to answer"Because the gate policy and the SPC engine are deliberately separate layers. The SPC engine's job is to surface every statistically meaningful pattern it can detect; the gate policy's job is to decide which of those patterns are severe enough to block a merge versus just warn about. Keeping the engine's coverage broad costs nothing — the dashboard and the WARN-level reasons still surface every triggered rule to a human, even the ones that don't block CI."

Nelson Rule 3 / Trend Detection

1. Plain EnglishThe score has been steadily climbing (or falling) for several builds in a row — even if no single point has crossed a control limit yet.
2. Technicalsrc/spc/trendDetection.ts's detectTrend() combines two independent signals: Nelson Rule 3 (6 consecutive strictly monotonic points) OR an ordinary-least-squares linear regression over the last 10 points, flagged significant when |correlation| ≥ 0.7 and the slope is non-zero.
3. What it detectsSlow, sustained drift in one direction — the "creeping accessibility debt" case a single-point rule structurally cannot see.
4. Why it mattersIt's the earliest possible warning: by the time a control-limit rule fires, a trend detector may have already been flagging the same builds for several cycles.
5. How this project uses itTrend defaults to a WARN in the gate policy, and only when direction === 'WORSENING' (an improving trend never produces a warning — see onlyWorsening: true).
6. Possible criticismCombining a pattern rule and a regression test in one detector could double-count the same underlying drift.
7. How to answer"That's deliberate redundancy, not double-counting — detected = nelson.triggered || regressionSignificant is a logical OR, so either signal alone is sufficient, and the reported result is a single boolean, not two separate warnings. The two methods catch slightly different shapes of drift: Nelson's rule needs strict monotonicity, the regression test tolerates small zig-zags as long as the overall correlation is strong."

Control-Limit Violations

1. Plain EnglishThe latest build's score literally crossed the UCL or LCL line on the chart.
2. Technicalsrc/spc/spcEngine.ts: uclViolation = latest > chart.uclX || latest < chart.lclX — a direct numeric comparison against the computed limits, independent of the rule evaluators.
3. What it detectsThe same "3-sigma breach" concept as WECO/Nelson Rule 1, checked as a direct arithmetic comparison rather than via the generic pattern-matching helper.
4. Why it mattersIt gives the gate policy a second, independent way to key off the same event (spc.failOnUclViolation: true), and it's what the dashboard highlights visually on the control chart.
5. How this project uses itSet to FAIL by default in gatePolicies.ts — spc.failOnUclViolation: true.
6. Possible criticism"Isn't this the same thing as WECO/Nelson Rule 1?"
7. How to answer"Almost exactly, yes — both are testing whether the latest point is beyond 3σ. I kept them as separate signals in the gate's reason list because they answer slightly different questions in the codebase: the rule evaluators scan a whole window for a pattern, while uclViolation is a direct, single-point comparison the engine also needs for the chart itself. Having both means the gate output stays honest about why it fired, even though the two often fire together."

Regression Spike Detection

1. Plain EnglishThis build's score jumped up by an unusually large amount compared to the last one, in the bad direction.
2. Technicalsrc/spc/regressionSpikeDetection.ts: detected = (latestMovingRange > uclMR) && (latest > previous) — both conditions required. The moving range must exceed its own control limit and the score must have gotten worse, not better.
3. What it detectsA same-build shock — one commit that visibly broke something, distinct from a slow trend.
4. Why it mattersIt's the fastest possible "something just broke" alarm — it only needs two data points (this build and the previous one) to fire, unlike the pattern rules which need a window of several.
5. How this project uses itAutomatic FAIL in the default policy (regression.onDetected: 'FAIL') — this is genuinely used in Experiment A, where it correctly fires at build 23, the exact build where the synthetic "deliberate regression" phase begins.
6. Possible criticismRequiring both conditions (large jump AND worsening direction) means a build that improves dramatically never counts as a "regression spike" — is that a gap?
7. How to answer"No — that's the point of the name. A large jump toward better accessibility isn't a regression, and penalizing it would be perverse. A large improvement can still register through other signals (e.g. it changes the center line for future builds), but it shouldn't itself trigger a failure."

CUSUM / Drift Detection

1. Plain EnglishNo single build looks alarming, but there's a small, consistent lean in one direction building up quietly across many builds.
2. Technicalsrc/spc/driftDetection.ts implements a two-sided tabular CUSUM: k = 0.5σ̂ (allowed slack), h = 5σ̂ (alarm threshold). Running sums accumulate max(0, x - (centerLine+k) + runningPlus) and the mirror image below the center line; direction = 'WORSENING' if the upper sum exceeds h, 'IMPROVING' if the lower sum does.
3. What it detectsSmall, sustained shifts too gradual for any single-point rule to catch — CUSUM is specifically designed to be more sensitive than Shewhart-style rules to small, persistent shifts.
4. Why it mattersIt complements the pattern rules and the trend detector: pattern rules need a strict shape (monotonic, alternating); CUSUM just needs a persistent lean, however irregular.
5. How this project uses itDefaults to WARN, and (like trend) only when direction === 'WORSENING' — an improving drift never triggers a warning.
6. Possible criticismCUSUM introduces two more tunable constants (k, h) — are 0.5σ and 5σ justified, or arbitrary?
7. How to answer"They're the textbook-standard tabular CUSUM defaults (k = half a sigma of allowed slack, h = 5 sigma of accumulated evidence before alarming) — not tuned specifically for this dataset. That's a reasonable, defensible starting point, and a documented limitation if asked whether they were validated empirically against this project's own telemetry — they weren't; there isn't yet enough real production history to tune them against."

Process Capability: Cpu / Cpk

1. Plain EnglishEven if the process is perfectly stable, is it stable at a good enough level? A process can be perfectly consistent and still consistently bad.
2. Technicalsrc/spc/capabilityAnalysis.ts: Cpu = (USL − X̄) / (3σ̂), a one-sided capability index against an upper specification limit (USL). capable = Cpu ≥ 1.33. If σ̂ = 0 (a perfectly flat series), Cpu is reported as null to avoid a division by zero, and capable falls back to a direct centerLine ≤ USL check.
3. What it detectsWhether the process's typical behavior, not just its worst moment, comfortably clears an agreed quality bar.
4. Why it mattersCpu < 1.0 means the process cannot reliably meet the specification even with zero special-cause events — that's a signal the baseline/policy needs attention, not any individual build.
5. How this project uses itOnly computed when a usl is explicitly supplied — the production path and Experiment A never supply one (capability is null for both). It's computed in Experiment B with USL = 40, producing Cpu ≈ 2.9811. Gate policy: Cpu < 1.33 → WARN, Cpu < 1.0 → FAIL.
6. Possible criticismWhy is capability analysis missing from Experiment A and from the real production history?
7. How to answer"See Why Cpk Was Excluded From Experiment A — it's a deliberate methodological choice, not an oversight. Capability analysis assumes one stable regime; Experiment A is deliberately five different regimes. Production history is simply too short (4 builds) for any capability number to be meaningful yet."
