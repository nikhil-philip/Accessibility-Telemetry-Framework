Academic honesty

Limitations

Every limitation below is real — checked against the actual code and data, not hedging language added for effect. Naming these clearly in a viva is a strength, not a weakness: it shows you understand the boundary between what's proven and what's assumed.

1. The core SPC methodology is validated on synthetic data, not real production history

Real production telemetry (telemetry/history/) currently has 4 records — far too few to validate a statistical detection methodology. Experiments A and B, which supply the real validated results in this guide (regression detection, Rule 1 behavior, Cpu≈2.9811), are both seeded, reproducible, synthetic cohorts.

Why it matters: the strongest possible research claim — that this methodology reduces false positives/negatives versus a static threshold, on real accessibility telemetry — cannot yet be made with confidence.

Why the project is still useful: it proves the machinery is implemented correctly, produces sensible and checkable results under known conditions, and is ready to be evaluated against real data the moment enough exists.

Future improvement: run the real CI pipeline against a real, evolving codebase for months, and re-evaluate RQ1–RQ3 against that accumulated history.

2. 30-build cohorts and finite samples

Both experiment cohorts contain exactly 30 builds. That's enough to exercise every qualitatively different scenario the gate policy cares about, but not enough for a strong statistical power claim about detection rates.

Why it matters: a reviewer could reasonably ask whether 30 builds is a large enough sample to trust any percentage-based claim (e.g., "X% of regressions detected").

Why the project is still useful: the experiments were designed as methodology validation (does the mechanism work correctly) rather than a statistical power study (how often does it work) — a smaller, controlled sample is appropriate for the former.

Future improvement: larger synthetic cohorts, or — better — real accumulated history, before making any percentage-based detection-rate claim.

3. The 15-build trailing window was not empirically tuned

DEFAULT_TRAILING_WINDOW_SIZE = 15 in src/spc/experimentAnalysis.ts is a reasonable SPC rule-of-thumb default, not the output of a sweep over candidate window sizes against real or synthetic data to find an optimum.

Why it matters: a different window size might trade off responsiveness and stability differently; 15 is defensible, not provably optimal.

Why the project is still useful: Experiment A's comparative analysis (expanding vs. trailing) is exactly the kind of study that could be repeated with different window sizes once more data exists.

Future improvement: a parameter sweep over window size against real accumulated telemetry, once available.

4. USL = 40 is an illustrative placeholder, not an organizationally derived specification limit

40 is copied from ARCHITECTURE.md's Appendix B example and reused unchanged in Experiment B (STABLE_COHORT_USL) and the dashboard (EXPERIMENT_B_USL), specifically to avoid picking a number that manufactures a favorable Cpu.

Why it matters: in a real deployment, the USL should come from an actual quality-policy conversation with real stakeholders — this project doesn't simulate that conversation.

Why the project is still useful: the capability-analysis machinery itself (the formula, the gate integration, the "capable" threshold) is correctly implemented and validated regardless of which USL is plugged in.

Future improvement: if deployed against a real project, USL should be set by whoever owns accessibility quality policy for that project, not inherited from this dissertation's example.

5. The I-MR chart's near-normality assumption is not empirically checked against this project's own data

ARCHITECTURE.md §9 names this directly as RQ3: does the weighted-score transform make the defect score's distribution defensibly close to normal, as I-MR charts assume, versus its likely-Poisson-like raw form? This project implements the chart; it does not report a distributional test of the actual telemetry against that assumption.

Why it matters: if the assumption doesn't hold well in practice, the stated "3-sigma" control limits may not carry their textbook false-alarm-rate interpretation.

Why the project is still useful: the weighted-score transform is a principled attempt to make the assumption more defensible than raw counts would be, even without a formal statistical test confirming it.

Future improvement: once real history accumulates, run a normality test (e.g. Shapiro-Wilk) against the real defectScore series and report the result — this is explicitly RQ3's open question.

6. Capability analysis assumes single-regime stability, which most real projects won't cleanly satisfy

Experiment B proves Cpk works correctly under an idealized single stable regime. A real project's accessibility history is unlikely to be that clean — it will have real regime changes (new features, refactors, team turnover) that make "when is it valid to compute Cpk" a genuinely hard, ongoing judgment call, not a one-time decision.

Why it matters: naively computing Cpk on real, messy history risks the exact misinterpretation Experiment A's exclusion was designed to avoid.

Why the project is still useful: the framework already demonstrates the correct discipline (don't compute Cpk on known-non-stationary data) — that discipline just needs to be applied by a human judgment call in real deployment, not automated away.

Future improvement: an automated stationarity/regime-change check that gates whether Cpk is even computed, rather than relying on a human to notice.

7. SPC rules can produce false positives — demonstrated, not just theoretical

Experiment A's "Rule 1 stuck" result is a real, observed false-positive-like behavior: under expanding history, one stale early outlier (build 1) kept triggering "beyond 3-sigma" for 16 consecutive builds, for a reason unrelated to any live problem.

Why it matters: a team using this gate under expanding-history analysis could see a persistent FAIL/WARN for a reason that isn't actually actionable.

Why the project is still useful: the mechanism is fully explainable and visible (the dashboard shows exactly which point triggered the rule), which is strictly better than an opaque false positive with no diagnosis path — and the trailing-window alternative demonstrably resolves it.

Future improvement: consider trailing-window analysis, or an automated "stale outlier" detector, as the default for production once enough history exists to make that choice meaningfully.

8. No long-term production history exists

This is the root cause behind several other limitations on this page. The project is young; real telemetry has accumulated for only a handful of builds.

Why it matters: almost every claim about the methodology's real-world usefulness (not just its correctness) is currently unverifiable.

Why the project is still useful: the pipeline is production-ready to start accumulating that history the moment it's deployed against a real, actively-developed codebase.

Future improvement: time — there's no substitute for actually running the pipeline for months against a real project.

9. CI environment differences

Development happened on Windows; CI runs on ubuntu-latest. src/telemetry/reporter.ts has a specific Windows workaround — a hardcoded list of common Git install paths — because some Windows shells don't expose git on PATH for spawned child processes even when it's installed.

Why it matters: that fallback list is not an exhaustive PATH resolution; on an unusual Windows setup it could still fail to resolve commitSha/branch, falling back to 'unknown' rather than crashing.

Why the project is still useful: the failure mode is safe (a placeholder value, not a crash), and CI itself — where it matters most for the gate to work reliably — runs on Linux where this workaround isn't needed.

Future improvement: a more general PATH-resolution strategy, or documenting the Git requirement explicitly for local Windows use.

10. Chromium-only browser coverage

Both the ShopSmart accessibility scan (CI installs only chromium) and the dashboard's own tests (playwright.dashboard.config.ts declares only a Desktop Chrome project) run on a single browser engine.

Why it matters: Firefox- or WebKit-specific rendering or accessibility-tree differences would not be caught, even though ARCHITECTURE.md §7 cites cross-browser support as a reason Playwright was chosen over Puppeteer.

Why the project is still useful: Chromium/axe-core coverage is still meaningful — most real-world accessibility defects are engine-agnostic (missing alt text, bad ARIA, poor contrast) — and the architecture supports adding more browser projects without any change to L4–L7.

Future improvement: add Firefox and WebKit projects to both Playwright configs once CI time budget allows.

11. Severity weights (10/5/2/1) and CUSUM constants are policy defaults, not empirically derived

Both the defect-score weighting and the CUSUM k/h multipliers follow common, documented conventions rather than being tuned against this project's own telemetry.

Why it matters: a different weighting or a different CUSUM sensitivity could change which builds trigger a WARN or FAIL, and there's no empirical evidence these specific numbers are the right ones for accessibility telemetry specifically (as opposed to generic software defect data).

Why the project is still useful: they're reasonable, industry-standard starting points, applied consistently and transparently (visible in gatePolicies.ts and driftDetection.ts as plain data, not hidden).

Future improvement: tune both against real accumulated telemetry once available.

12. ARCHITECTURE.md has drifted from the implementation in several small, named ways

See Architecture → Discrepancies for the full table — no spc.config.ts, no default 25-build window, richer rule coverage than described, extra undocumented detectors, and file-naming differences.

Why it matters: a reviewer who read the architecture document before the code could reasonably ask about any of these mismatches.

Why the project is still useful: none of the drift represents a correctness bug — every regression-guard script passes against the actual code — and being able to name the drift accurately is itself evidence of understanding the real system.

Future improvement: a documentation pass reconciling ARCHITECTURE.md with the as-built system (this guide is, in effect, a first step toward that).

13. The ShopSmart violation catalog's own documentation has an off-by-one

docs/violations/catalog.md states "80" seeded violation instances; directly counting instanceId entries in docs/violations/catalog.json gives 81.

Why it matters: it's a small but real inconsistency in the project's own ground-truth documentation.

Why the project is still useful: the underlying data (catalog.json) is internally consistent and is what the build manifests actually cross-check against — the discrepancy is in one summary sentence in prose, not in the data used by any code.

Future improvement: a one-line fix to catalog.md's prose count.

14. No automated detection of a changed measurement definition

If the WCAG tag set, the axe-core version, or the scanned route list changes, defectScore can shift for reasons unrelated to any real accessibility regression — and the SPC engine has no way to know its own measurement definition changed underneath it.

Why it matters: this is both an honest robustness gap and, more pointedly, an unaddressed way the gate could be gamed (see Reviewer Q&A → Difficult, Q51).

Why the project is still useful: configuration changes go through the same version-controlled PR review as any other code change, so the change itself is at least visible in a diff, even if not automatically flagged to the SPC engine.

Future improvement: version the measurement configuration itself and have the SPC engine treat a version change as a regime boundary, similar to how Experiment A's phases are handled.

15. JSON-file telemetry persistence doesn't scale indefinitely

Named directly in ARCHITECTURE.md §9's threats to validity: one JSON file per build in telemetry/history/ is fine at dissertation scale, but won't scale cleanly to a project with thousands of historical builds.

Why it matters: loadTelemetryHistory() reads every file in the directory on every SPC computation — a real, long-running project would eventually pay a real I/O cost for this.

Why the project is still useful: JSON persistence gives a full audit trail, human readability, and diffability in pull requests essentially for free, at a scale (dozens to low hundreds of builds) this project actually operates at.

Future improvement: a real time-series store (SQLite/Postgres), as ARCHITECTURE.md §7 already names as the considered, deliberately-deferred alternative.

Every limitation above is checked against the actual repository — none are hypothetical hedging. See Tough Questions for how to discuss several of these live, and Architecture → Discrepancies for the full documentation-drift table.
