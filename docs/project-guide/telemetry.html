Layer 4

Telemetry: Turning a Scan Into History

Telemetry is what makes this project a process monitor instead of a one-off test runner. Every build leaves a permanent, small trace, and it's that trace, accumulated over time, that the SPC engine reasons over.

What Is Telemetry, Here?

Beginner explanation

Telemetry just means "measurements collected automatically, over time." In this project, every time the accessibility tests run, the system writes down one small file describing how that run went — how many accessibility problems were found, how severe they were, and a single summary number. Nothing is discarded; every one of those files stays around, so later you can look back and see the whole history.

Technical explanation

Concretely, telemetry is a versioned, schema-typed JSON record (TelemetryRecord, defined once in src/telemetry/schema.ts) written once per test run to telemetry/history/build-<commitSha>.json. The schema is the single source of truth both the collector (which writes it) and the SPC engine (which reads it) import — so the two can never silently drift apart without a TypeScript compile error.

Why Do We Store Telemetry At All?

Beginner explanation

If you only ever look at "did this one build pass or fail," you can never tell whether things are getting better or worse over time — you only see one frame of a movie. Storing every build's number lets you watch the whole movie: is the defect score bouncing around a stable average, or is it climbing?

What Is defectScore?

It's the one number every other layer of this project actually cares about — the "individual measurement" the control chart plots.

// src/telemetry/collector.ts
const SEVERITY_WEIGHT = { critical: 10, serious: 5, moderate: 2, minor: 1 };

function computeDefectScore(violationsBySeverity) {
  return violationsBySeverity.critical * 10
       + violationsBySeverity.serious  * 5
       + violationsBySeverity.moderate * 2
       + violationsBySeverity.minor    * 1;
}

For the example record above: 0×10 + 4×5 + 0×2 + 2×1 = 22, matching "defectScore": 22 exactly.

Technical explanation

This mirrors the classic severity-weighted defect density formula from software quality engineering: it exists so that one critical WCAG failure isn't statistically invisible next to ten minor ones. A page with 10 minor violations (score 10) is treated as less serious than a page with a single critical violation (score 10 needs 2 critical... actually 1 critical alone already scores 10) — the weighting is deliberately front-loaded toward severity, not raw count.

Possible reviewer question

"Why these specific weights — 10/5/2/1 — and not something else?" Be honest: this is a fixed, documented policy choice (ARCHITECTURE.md §8.2), not something empirically derived from data in this project. It mirrors a common industry convention for severity-weighted defect density; it was not tuned against ShopSmart's own violation distribution. That's a reasonable thing to say plainly if asked — see Limitations.

Beginner explanation

Think of telemetry/history/ as your real diary — only 4 entries so far, because the project is young. telemetry/experiments/ is more like a flight simulator: synthetic scenarios built to test whether the statistics behave correctly under conditions (30 builds, a known regression, a known stable process) that the real diary doesn't have enough entries to show yet.

Why Is CI-Generated Telemetry Artifact-Only?

When the GitHub Actions workflow runs the accessibility scan, it writes a brand-new telemetry/history/build-<sha>.json file — but that file is never committed back into the repository. It leaves the CI runner only as a downloadable workflow artifact.

Technical explanation

The workflow declares permissions: contents: read at the top of .github/workflows/accessibility-ci.yml, with the comment "this workflow never pushes, comments, or deploys; it only reads the checked-out repo and uploads artifacts." There is no git commit or git push step anywhere in the file. The only way the new record leaves the runner is:

- name: Upload quality evidence (dashboard, telemetry, gate verdict, reports)
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: quality-evidence-${{ github.run_id }}
    path: |
      dashboard/
      telemetry/aggregated/
      telemetry/history/
      reports/
    if-no-files-found: warn
    retention-days: 30
What I should say

"I kept CI read-only on purpose. If the pipeline could push commits back into the repository, every CI run would create a new commit, and that gets messy fast — merge conflicts on a shared branch, an ever-growing history nobody curates, and a workflow that suddenly needs write credentials it didn't need before. Instead, the new telemetry record is captured as a 30-day workflow artifact — the evidence is preserved and downloadable, but the repository itself only grows when a human deliberately commits a new baseline build."

Sources: src/telemetry/schema.ts, collector.ts, writer.ts, reporter.ts; real files in telemetry/history/ and telemetry/experiments/; .github/workflows/accessibility-ci.yml.
