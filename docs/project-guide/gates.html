Layer 6

Quality Gates: PASS, WARN, FAIL

The gate is where every statistical signal from L5 (SPC) and every raw number from L4 (telemetry) gets turned into one decision. It's a policy, expressed as data, applied by one pure function.

Overall status, exactly as coded in qualityGateEvaluator.ts's deriveStatus():

if (reasons.some(r => r.severity === 'FAIL')) return 'FAIL';
if (reasons.some(r => r.severity === 'WARN')) return 'WARN';
return 'PASS';

PASS = zero reasons triggered at all. WARN = at least one WARN reason and zero FAIL reasons. FAIL = at least one FAIL reason, regardless of how many WARNs also fired.

Exit Codes: PASS → 0, WARN → 0, FAIL → 1

The pipeline is strictly one-directional: policy (gatePolicies.ts) → evaluator → verdict → CI adapter → exit code → scripts/run-quality-gate.ts's I/O.
// src/gates/ciAdapter.ts
export function formatGateVerdictForCi(verdict: GateVerdict): CiGateReport {
  const exitCode: 0 | 1 = verdict.status === 'FAIL' ? 1 : 0;
  ...
}

The comment on CiGateReport.exitCode states the policy directly: "0 for PASS/WARN, 1 for FAIL — WARN must never fail the CI job (ARCHITECTURE.md §8.5 / project policy)."

Why Doesn't WARN Block CI?

What I should say

"WARN exists for signals that are worth a human noticing but don't justify stopping the whole team's work automatically — a trend that's worsening but hasn't crossed a hard limit, or a capability index that's slipped below the comfortable 1.33 threshold but not below the unacceptable 1.0 one. If WARN blocked CI, it would behave identically to FAIL, and then there'd be no reason to have two separate severities at all. The dashboard still surfaces every WARN reason, so nothing is silently dropped — it's visible, it's just not a hard stop."

Why Doesn't ciAdapter.ts Contain Statistical Policy?

src/gates/ciAdapter.ts's own header comment states its scope precisely: "This file computes no thresholds, re-derives no PASS/WARN/FAIL decision, and reads no telemetry — it is pure formatting over a verdict that already exists by the time it's called." It imports only the GateVerdict type — not gatePolicies.ts, not any SPC module. Every number that decides PASS/WARN/FAIL lives exclusively in gatePolicies.ts's DEFAULT_GATE_POLICY.

Technical explanation

This separation is enforced by design, not just convention: gatePolicies.ts's own docstring for GatePolicyConfig states, "Every threshold is data, not code … so a policy change never requires touching qualityGateEvaluator.ts." The pipeline is strictly: policy (thresholds) → evaluator (applies thresholds, produces a verdict) → CI adapter (formats the verdict, no thresholds) → I/O script (writes files, sets exit code). Kept pure — no fs, no process.*, no console.* — ciAdapter.ts is directly unit-testable by scripts/verify-ci.ts without a real telemetry/history/ or a real CI environment.

Possible reviewer question

"What's the actual benefit of this separation, beyond tidiness?" If the accessibility thresholds ever need to change — say, tightening maxSeriousDefects from 5 to 3 — that's a one-line change in a plain data object in gatePolicies.ts. Nobody touches CI YAML, nobody touches the evaluator, nobody touches the exit-code logic. That's a real, demonstrable reduction in the blast radius of a policy change, and it's also why ciAdapter.ts can be tested with fixed, hand-built verdicts instead of needing a live gate evaluation.
