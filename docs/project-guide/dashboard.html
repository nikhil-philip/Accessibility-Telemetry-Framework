Layer 7

Dashboard: Presentation Only

The dashboard is a static site generated on demand. Its entire job is to display numbers that L4, L5, and L6 already computed — it is not allowed to calculate a single one of its own, and that constraint is enforced by an automated check, not just a design intention.

What the Dashboard Displays

Three panels, rendered by src/dashboard/templates/dashboard.js's render(data):

  1. Production Process (from telemetry/history/) — a gate-status badge row (Gate: PASS/WARN/FAIL, SPC process state, SPC stability status), the list of gate-failure reasons with actual vs. threshold values, stat tiles (latest defect score, center line, control limits, capability/Cpu), a violations-by-severity breakdown, and the I-chart itself with a "View as table" toggle.
  2. Experiment A — two side-by-side columns (Expanding History vs. Trailing Window), each with its own stat tiles (gate outcomes, regression spikes, trend/drift detections) and its own control chart with phase bands, plus an observations list.
  3. Experiment B — stat tiles (Cpu, capable badge, center line, gate status) and a control chart with an added USL reference line.

Where Its Data Comes From

src/dashboard/dashboardDataBuilder.ts's buildDashboardData() calls, and only calls:

  • loadTelemetryHistory() — production history, and separately, both experiment cohort directories.
  • computeSpcReport() — the production SpcReport, and Experiment B's (with usl: EXPERIMENT_B_USL, which equals 40).
  • evaluateLatestBuild() / evaluateQualityGate() — the production gate verdict, and Experiment B's.
  • runAnalysis() / summarizeResults() (from src/spc/experimentAnalysis.ts) — Experiment A's walk-forward results, under both history-selection methods.

Why It Doesn't Duplicate SPC/Gate Calculations

Technical explanation

dashboardDataBuilder.ts's own header comment: "This module performs zero SPC math, zero rule evaluation, zero gate policy logic, and zero score computation of its own — it only reads telemetry off disk … and groups already-computed results into the shape src/dashboard/types.ts declares." The only numeric literal the file defines is EXPERIMENT_B_USL = 40, and that's documented as an existing option value passed into the unmodified computeSpcReport() — not a new calculation. types.ts reinforces this: "Every field here is a re-export or a plain grouping of a type already defined by L4 … L5 … L6 … This file declares zero new score, statistic, or threshold types."

The template's presentation layer says the same thing to the end user, in the actual footer of the generated site (src/dashboard/templates/index.html):

<p>Presentation layer only — every value on this page is read
directly from data.json, itself produced by the unmodified L4
(Telemetry), L5 (SPC Analytics), and L6 (Quality Gate) engines.
No score, control limit, rule, or capability calculation is
performed by this page.</p>
Technical explanation — how this is enforced, not just claimed

scripts/verify-dashboard.ts calls buildDashboardData() and then, separately, calls computeSpcReport(history) and evaluateLatestBuild(history) directly — and asserts the two outputs are byte-identical (modulo the generatedAt timestamp). It also independently recomputes defectScore from the raw severity counts and checks it against the record, and diffs telemetry/history/ and both experiment directories before and after calling buildDashboardData() twice, to prove the dashboard never mutates its source data.

Generating and Serving It

  • scripts/generate-dashboard.ts calls buildDashboardData(), writes the result to telemetry/aggregated/dashboard-data.json and dashboard/data.json, and copies src/dashboard/templates/{index.html,dashboard.css,dashboard.js} verbatim into dashboard/. It contains no markup or rendering logic itself — only file I/O.
  • scripts/serve-dashboard.ts is a minimal, dependency-free static file server (Node's built-in http/fs only, default port 4310) that exists purely so Playwright can load the dashboard over http:// — fetch('data.json') is blocked by Chromium over a raw file:// path.
  • The dashboard/ folder itself is git-ignored and not present in the checked-out repository until one of the above scripts runs — this is expected, not missing.

Browser Smoke Tests

tests-dashboard/dashboard.smoke.spec.ts, run via playwright.dashboard.config.ts (Chromium only, base URL http://localhost:4310). It proves the page actually works in a real browser:

  • Loads /index.html, checks the response is 200 OK and the <h1> reads "Accessibility Quality Engineering Dashboard."
  • Confirms the production panel shows a gate badge, "Latest defect score," and severity labels ("Critical (weight 10)," "Serious (weight 5)").
  • Confirms the I-chart's SVG actually rendered data points (svg.chart circle.point count > 0).
  • Confirms at least one SPC observation is visible and mentions "regression spike" or "rule 1."

Keyboard Accessibility

The same smoke spec presses Tab up to 40 times looking for the first "View as table" button by keyboard focus, then presses Enter and asserts the data table becomes visible — proving the dashboard's interactive elements are reachable and operable without a mouse. It also asserts zero uncaught page errors and zero console errors during the whole run.

Dashboard Accessibility (axe-core, Dogfooding)

tests-dashboard/dashboard.a11y.spec.ts uses the project's own shared createAxeBuilder() helper (the same one used to scan ShopSmart) and asserts zero axe-core violations — the actual code:

for (const colorScheme of ['light', 'dark'] as const) {
  test(`dashboard has zero axe-core violations (${colorScheme} mode)`, async ({ browser }) => {
    const context = await browser.newContext({ colorScheme });
    const page = await context.newPage();
    await page.goto('/index.html');
    await page.waitForLoadState('networkidle');
    const results = await createAxeBuilder(page).analyze();
    expect(results.violations, JSON.stringify(results.violations, null, 2)).toEqual([]);
    await context.close();
  });
}

This runs the check twice — once per colorScheme — so both light and dark mode are independently verified against real CSS (dashboard.css defines color-scheme: light by default and a @media (prefers-color-scheme: dark) block).

What I should say

"It felt important that a project about accessibility didn't ship an inaccessible dashboard. So the dashboard gets scanned with the exact same axe-core configuration used on the application under test, in both light and dark mode, and that test is wired into CI as a required step — not a nice-to-have I ran once manually."
